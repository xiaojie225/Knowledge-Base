### 总结：微信小程序实现原理（双线程架构）

#### 1. 核心知识点
*   **双线程架构**：采用 `Hybrid` 渲染，将界面和逻辑拆分为两个独立线程：
    *   **渲染层（View）**：使用 `WebView` 渲染界面，每个页面对应一个 `WebView` 线程。
    *   **逻辑层（App Service）**：运行在 `JSCore` 线程中，负责执行 JS 业务逻辑。
*   **通信机制**：基于数据驱动，通过宿主环境桥接，将 `setData` 数据传至渲染层，并拦截页面交互事件反馈给逻辑层。
*   **运行机制**：
    *   **冷启动**：重新加载代码包并初始化。
    *   **热启动**：将后台运行态切换至前台，无需重新加载。
    *   **生命周期/销毁**：内存压力或后台超时会被主动销毁。

#### 2. 设计思想
*   **性能隔离**：借鉴 `JS` 单线程互斥特性，通过双线程分离，避免复杂的 JS 计算阻塞页面渲染。
*   **异步通信**：视图层与逻辑层数据同步存在时延，采用异步更新机制，通过初始化时序控制确保数据准确性。

#### 3. 为什么这样实现？
*   **稳定性**：脚本逻辑放入独立线程，复杂业务逻辑不会导致 UI 线程卡死。
*   **安全性**：通过特定接口 (`setData`/事件触发) 限制对 DOM 的直接操作，保证宿主环境可控。

#### 4. 应用场景
*   **跨端开发**：用于需要高性能、高安全性且要求原生 App 体验的跨平台应用容器。

### 题

#### 简单题
1.  **简述微信小程序的双线程结构分别是什么？**
    *   答：渲染层（View）基于 WebView 渲染；逻辑层（App Service）基于 JSCore 运行 JS 代码。
2.  **什么是小程序的“冷启动”和“热启动”？**
    *   答：冷启动是小程序首次打开或被销毁后重新加载；热启动是后台态小程序切回前台，无需重新下载加载。
3.  **小程序中为什么数据更新是异步的？**
    *   答：由于渲染层和逻辑层是两个独立线程，数据传递需经过线程间通信且有延时，故采用异步更新。
4.  **页面奔溃的常见原因是什么？**
    *   答：页面内存溢出。系统内存警告或运行状态过久，微信会主动销毁小程序。
5.  **逻辑层与渲染层如何通信？**
    *   答：逻辑层通过 `setData` 发送数据；交互事件拦截后，通过桥接转发给逻辑层。

#### 中等题
1.  **WebView 渲染与传统的浏览器渲染有何不同？**
    *   答：传统网页中脚本和 UI 渲染在同一线程，JS 执行会阻塞 UI；小程序通过双线程架构，将 JS 逻辑剥离到 JSCore 线程，实现了渲染与逻辑的并行。
2.  **小程序发布新版本后，用户能否立即体验到？**
    *   答：不能立即生效。每次冷启动检查更新并异步下载，需等下一次冷启动时才应用新版本，保证启动速度和版本的一致性。

### 总结：微信小程序优化手段

#### 1. 核心知识点
*   **启动优化**：小程序启动涉及代码包下载、加载及首页初始化。核心在于**减小包体积**（压缩代码、清理无用资源、图片网络化）和**分包加载**（利用分包预加载技术）。
*   **渲染优化**：
    *   **数据请求**：尽早请求（`onLoad`）、利用本地缓存（`StorageSync`）、利用骨架屏。
    *   **`setData` 策略**：避免频繁调用、减少数据通信量（不在界面展示的数据不要传）、不在 `data` 中存储无关渲染的复杂数据。
    *   **模块化**：将独立模块抽离为自定义组件，实现局部更新。

#### 2. 设计思想
*   **体验先行**：通过预加载和本地缓存缩短“感知时间”，即使代码包下载慢，也能通过骨架屏或缓存实现页面秒开。
*   **资源节约**：遵循“按需加载”原则，避免单次加载过多无用资源，减小渲染线程与逻辑线程间的通信压力。

#### 3. 为什么这么写？
*   **通信开销**：`setData` 涉及跨线程通信，数据量大或更新频率高直接影响响应速度。
*   **内存优化**：合理使用存储和分包，能有效预防内存溢出导致的崩溃。

#### 4. 应用场景
*   适用于所有复杂业务场景的小程序，特别是首屏加载慢或页面交互卡顿严重的场景。

### 面试题

#### 简单题
1.  **如何减小微信小程序包的体积？**
    *   答：上传时开启压缩选项；清理无用代码和资源；将大图片放入服务器，小程序内仅放小 icon；使用分包加载。

    *   答：在用户点击子包页面前，提前在后台自动下载子包，减少用户访问时的等待时间。
3.  **为什么不建议在 `data` 中存储渲染无关的数据？**
    *   答：`setData` 会触发页面渲染，通信量与数据结构复杂度正相关，无关数据会增加通信负担和内存开销。
4.  **如何优化小程序的首屏渲染时间？**
    *   答：`onLoad` 尽早请求数据；使用本地缓存减少 HTTP 请求；使用骨架屏占位；利用前置页面带入的数据。
5.  **自定义组件更新为什么能提升渲染效率？**
    *   答：组件拥有独立的数据空间和 `setData` 环境，更新组件不会触发整个页面的重新渲染。

#### 中等题
1.  **频繁使用 `setData` 会导致什么问题？如何改进？**
    *   答：会导致渲染线程与逻辑线程通信频繁，产生时延并阻塞界面响应。改进：将多次 `setData` 合并为一次，或通过自定义组件实现局部渲染。
2.  **解释为什么小程序在访问子包时会卡顿？你如何优化？**
    *   答：因为子包需要动态下载。优化：合理规划分包大小，使用分包预加载技术，在用户访问前完成下载。

### 总结：微信小程序路由跳转

#### 1. 核心知识点
*   **页面管理**：小程序采用**栈（Stack）**的形式管理 `pageModel`。
*   **跳转方式**：
    *   `wx.navigateTo`：保留当前页，跳转到应用内页面（新页入栈）。
    *   `wx.redirectTo`：关闭当前页，跳转到应用内页面（出栈后入栈）。
    *   `wx.switchTab`：跳转到 `tabBar` 页，关闭所有非 `tabBar` 页面（全出栈，仅留新 Tab）。
    *   `wx.navigateBack`：关闭当前页，返回上一或多级页面（出栈）。
    *   `wx.reLaunch`：关闭所有页面，打开到应用内某页面（全出栈，仅留新页面）。

#### 2. 设计思想
*   **内存优化**：页面栈限制 10 层。当页面过多或跳转频繁时，使用 `redirectTo` 代替 `navigateTo` 可释放非必要页面的内存占用，防止应用奔溃。
*   **路由权衡**：`navigateTo` 体验较好但占用内存，`redirectTo` 节约内存但需重新加载。根据业务场景（页面访问深度、资源消耗）合理选择跳转策略。

#### 3. 为什么怎么写？
*   **栈管理**：为了实现精准的后退逻辑（`delta` 参数）和状态维持。
*   **内存清理**：针对微信环境严格的内存限制，通过关闭页面（栈操作）来主动清理内存。

#### 4. 应用场景
*   **一般跳转**：推荐 `navigateTo`，利于快速返回。
*   **复杂场景**：多级跳转、登录后跳转至首页，使用 `reLaunch`；跳转至 `tabBar` 页面，必须使用 `switchTab`。

### 总结：微信小程序生命周期

#### 1. 核心知识点
小程序生命周期分为三层，各司其职：
*   **应用生命周期**（`App`）：监听整个小程序的全局事件，如初始化 (`onLaunch`)、启动/切换前台 (`onShow`)、进入后台 (`onHide`)。
*   **页面生命周期**（`Page`）：监听单个页面的完整流转，如加载 (`onLoad`)、渲染完成 (`onReady`)、卸载 (`onUnload`)。
*   **组件生命周期**（`Component`）：关注组件自身挂载状态，包含创建 (`created`)、挂载 (`attached`)、销毁 (`detached`)，还可监听所在页面的显隐。

### 应用的生命周期

| 生命周期               | 说明                                    |
| ---------------------- | --------------------------------------- |
| onLaunch               | 小程序初始化完成时触发，全局只触发一次  |
| onShow                 | 小程序启动，或从后台进入前台显示时触发  |
| onHide                 | 小程序从前台进入后台时触发              |
| onError                | 小程序发生脚本错误或 API 调用报错时触发 |
| onPageNotFound         | 小程序要打开的页面不存在时触发          |
| onUnhandledRejection() | 小程序有未处理的 Promise 拒绝时触发     |
| onThemeChange          | 系统切换主题时触发                      |

### 页面的生命周期

| 生命周期 | 说明                              | 作用                           |
| -------- | --------------------------------- | ------------------------------ |
| onLoad   | 生命周期回调—监听页面加载         | 发送请求获取数据               |
| onShow   | 生命周期回调—监听页面显示         | 请求数据                       |
| onReady  | 生命周期回调—监听页面初次渲染完成 | 获取页面元素（少用）           |
| onHide   | 生命周期回调—监听页面隐藏         | 终止任务，如定时器或者播放音乐 |
| onUnload | 生命周期回调—监听页面卸载         | 终止任务                       |

### 组件的生命周期

| 生命周期 | 说明                              |
| -------- | --------------------------------- |
| created  | 生命周期回调—监听页面加载         |
| attached | 生命周期回调—监听页面显示         |
| ready    | 生命周期回调—监听页面初次渲染完成 |
| moved    | 生命周期回调—监听页面隐藏         |
| detached | 生命周期回调—监听页面卸载         |
| error    | 每当组件方法抛出错误时执行        |

注意的是：

- 组件实例刚刚被创建好时， created 生命周期被触发，此时，组件数据 this.data 就是在 Component  构造器中定义的数据 data ， 此时不能调用 setData
- 在组件完全初始化完毕、进入页面节点树后， attached 生命周期被触发。此时， this.data 已被初始化为组件的当前值。这个生命周期很有用，绝大多数初始化工作可以在这个时机进行
- 在组件离开页面节点树后， detached 生命周期被触发。退出一个页面时，如果组件还在页面节点树中，则  detached 会被触发

#### 2. 设计思想
*   **分层管理**：通过分离全局、页面、组件三级生命周期，实现职责解耦，便于在对应时机进行数据请求、资源销毁和渲染初始化。
*   **事件驱动**：框架通过预定义的生命周期回调，让开发者在特定框架节点执行业务逻辑，保证执行流与小程序运行状态高度一致。

#### 3. 执行流程与顺序
*   **启动顺序**：`App.onLaunch` -> `App.onShow` -> `Page.onLoad` -> `Page.onShow` -> `Page.onReady`。
*   **页面跳转**：跳转时触发旧页面的 `onHide`，随后触发新页面的 `onLoad`、`onShow` 和 `onReady`。
*   **返回页面**：触发当前页面的 `onUnload`（若销毁）或 `onHide`，再触发出现在前台页面的 `onShow`。

#### 4. 关键点
*   组件的 `created` 阶段无法调用 `setData`，初始化数据应放在 `attached` 阶段。
*   `onReady` 在页面初次渲染完成后触发，一个页面生命周期内只触发一次。

### 总结：微信小程序登录流程

#### 1. 核心知识点
*   **关键概念**：
    *   `code`：由 `wx.login()` 生成，是换取 `openid` 和 `session_key` 的凭证。
    *   `openid`：用户在该小程序下的唯一标识。
    *   `session_key`：服务器端用于数据加密签名的密钥，不可传输。
*   **登录流程**：小程序通过 `wx.login()` 获取 `code`，发送给开发者后端；开发者后端携带 `appid`、`appsecret` 和 `code` 向微信服务器换取 `openid` 和 `session_key`；开发者后端根据 `openid` 创建/绑定本地用户体系，生成自定义登录态（Session/Token）返回小程序。

#### 2. 设计思想
*   **安全隔离**：`session_key` 严禁在网络上传输，通过后端服务器作为中间层与微信服务器交互，保护小程序核心密钥安全。
*   **多端协同**：小程序侧负责获取临时凭证（`code`）并存储登录态，后端负责校验微信凭证、维护用户注册体系及分发业务令牌。

#### 3. 为什么这么写？
*   **防篡改**：前端仅负责发起请求，校验和身份注册由拥有 `appsecret` 的服务端执行，确保登录真实可信。
*   **状态维护**：通过将自定义登录态（Session）存入 `Storage`，实现用户免重复登录，且过期机制由服务端灵活管控。

#### 4. 扩展机制
*   **登录态校验**：
    *   方案 A：后端通过对比自定义 Token 有效期来判断。
    *   方案 B：使用 `wx.checkSession` 在小程序端检查微信态，若过期则触发完整登录逻辑。

#### 简单题
1.  **登录流程中 `wx.login()` 的作用是什么？**
    *   答：获取用户的临时登录凭证 `code`。
2.  **`openid` 的作用是什么？**

5.  **微信登录为什么需要开发者后端参与？**
    *   答：因为换取凭证需要 `appsecret`（安全密钥），必须在受控的服务器后台运行，前端无法保护此密钥。

#### 中等题
1.  **详细描述小程序获取用户信息并注册/登录的全流程。**
    *   答：① `wx.login()` 获取 `code`；② 小程序传 `code` 给后端；③ 后端调用微信接口换取 `openid` 和 `session_key`；④ 后端根据 `openid` 查询用户；⑤ 若不存在则注册，最后生成自定义 Session 返回前端；⑥ 小程序本地缓存 Session，后续请求携带。
2.  **`wx.checkSession` 和服务端自定义登录态对比，哪个更优？**

### 总结：微信小程序支付流程

#### 1. 核心知识点
*   **支付核心接口**：`wx.requestPayment()`，用于在小程序端调起微信支付控件。
*   **交互机制**：
    *   前端：发起下单请求，携带商品及 `openid` 等信息。
    *   后端：与微信支付服务器交互，获取预付单信息（`prepay_id`），并进行签名计算。
    *   流程闭环：前端拿到后端返回的支付参数（时间戳、随机串、签名等），调用支付接口；微信侧完成支付后，分别通知前端（用户侧）和后端（订单状态更新）。

#### 2. 设计思想
*   **前后端分离的安全性**：预付单的申请、签名及关键校验逻辑均在后端完成，前端只负责调用接口调起支付，防止敏感参数被恶意篡改。
*   **双向验证**：支付结果不仅通知前端，更重要的是通过服务器异步通知确认支付状态，保证数据准确性与交易可靠性。

#### 3. 为什么这么写？
*   **简化流程**：相比网页支付，小程序无需设置支付目录和域名授权，开发更高效。
*   **安全性**：使用 `prepay_id` 作为会话凭证，配合后端加密签名，保障每一笔交易在微信后台均可鉴权验证。

#### 4. 应用场景
*   适用于所有涉及交易、会员充值或虚拟服务购买的小程序电商场景。

### 面试题

#### 简单题
1.  **小程序中调起支付使用哪个 API？**
    *   答：`wx.requestPayment()`。
2.  **支付流程中 `prepay_id` 是由谁生成的？**
    *   答：后端服务器在向微信统一下单接口请求后获取。
3.  **前端调用 `wx.requestPayment` 需要哪些必要参数？**
    *   答：`timeStamp`（时间戳）、`nonceStr`（随机串）、`package`（prepay_id）、`signType`（签名方式）、`paySign`（签名）。
4.  **支付成功后，后端如何更新订单状态？**
    *   答：通过微信服务器下发的支付通知接口。
5.  **微信支付为什么要后端签名？**
    *   答：防止数据在前端被篡改，确保支付请求的合法性和安全性。

#### 中等题
1.  **简述小程序完整支付流程。**
    *   答：① 小程序发起下单请求；② 后端换取 `openid` 并向微信统一下单获取 `prepay_id`；③ 后端对参数签名并返回给小程序；④ 小程序调用 `wx.requestPayment`；⑤ 微信鉴权并处理支付；⑥ 微信服务器通知后端支付结果，后端更新订单状态。
2.  **前端收到支付成功的回调就代表订单支付成功了吗？**
    *   答：不一定。前端回调仅作为用户界面的反馈，最终的订单状态以微信服务端回调通知后端服务器确认的结果为准。
